# Android testing and QA

## Choose the cheapest test that can fail for the right reason

- Pure Kotlin/domain rule: JUnit test in `core`.
- Tool schema/validation/dispatch: JUnit test with a fake tool context or a real dispatcher.
- File persistence: temp directory, real store, corruption and restart cases.
- Compose component/screen: Compose UI test, only when the interaction or rendering is the risk.
- Android port/service: instrumentation test with a device/emulator; compile it in CI even without a
  device.
- End-to-end flow: one focused acceptance test, not a suite of duplicate happy paths.

## Test structure

Use Arrange–Act–Assert and one behavior per test. Name the behavior, not the implementation. Prefer
real domain objects over mocks; fake only at a boundary (network, clock, file system, Android port).
Use a fixed clock and deterministic ids where output is compared.

## Must-cover cases for career work

- Profile validation: blank required fields, invalid dates, unconfirmed facts.
- Truth guard: an invented employer or metric is rejected.
- Job extraction: missing title/company stays empty, never guessed.
- Duplicate detection: same URL and same title/company/location.
- Suspicious listing: upfront payment, contact-only application, unrealistic pay.
- Matching: missing must-have skill caps the score; explanation mentions the gap.
- Application transitions: illegal jumps rejected; approval and evidence required.
- Submission: a model/agent cannot mark submitted; verification requires the reference in the text.
- Form mapping: sensitive fields are handed to the user; no auto-fill.
- Storage: atomic write, corrupt-file backup, schema version, erase.
- DOCX/PDF: generated bytes are readable and contain the confirmed facts.

## Running

- `./gradlew :core:test` for the core suite.
- `./gradlew :app:testDebugUnitTest` for app unit tests.
- `./gradlew :app:compileDebugAndroidTestKotlin` to check instrumentation code compiles.
- `./gradlew :app:connectedDebugAndroidTest` only with a connected device/emulator.

When filtering output through a pipe, preserve the exit status (`set -o pipefail` or capture it).
Read the failure, fix the cause, rerun the affected test. Do not weaken assertions or skip a failing
test to make a build green.

## Regression discipline

- Add a test for every bug fix that can regress.
- Keep golden/prompt tests intentional: update them only after reviewing the actual prompt/tool diff.
- Cover migration from the previous schema with a fixture, not just the current happy path.
- Report tests that could not run and why. "Compiled" is not "tested"; "tested" is not "verified on a
  device".
